# 超大目录导入与扫描优化设计

## 1. 目标
解决用户在导入包含约 18000 张图片的大目录时，点击“使用此文件夹”后长时间无响应甚至看似失败的问题。

## 2. 问题分析
当前流程在用户选择目录后，会立即执行完整扫描：
- `MainActivity.kt` 中在 `OpenDocumentTree` 返回后立刻调用 `FileScanner(context).scanFolder(...)`
- `FileScanner.kt` 当前基于 `DocumentFile.listFiles()` 遍历整个目录

对于包含海量文件的目录，这里有两个性能瓶颈：
1. **系统文件选择器本身**在进入超大目录时就可能卡住，因为它要预读取/枚举内容。
2. **应用扫描器**使用 `DocumentFile.listFiles()`，在大目录下性能非常差。

## 3. 设计方案

### 3.1 用户体验优化：先加入列表，再后台扫描
- 用户点击“使用此文件夹”后：
  1. 立即把文件夹信息写入数据库并显示到 UI 列表。
  2. UI 给出状态：`正在扫描...`
  3. 真正的文件扫描改为后台协程执行。
- 这样即使扫描需要几分钟，用户也会感觉“添加成功了，只是在后台建立索引”。

### 3.2 扫描实现优化：替换慢接口
- 当前：`DocumentFile.listFiles()`
- 目标：改用 Android 的 `DocumentsContract` / `ContentResolver.query(...)` 直接查询文档树节点。
- 原因：
  - `DocumentFile` 是对文档接口的高层封装，使用方便，但在大目录下性能非常差。
  - `DocumentsContract` 能直接分页/批量拿到子节点元数据，更适合大规模扫描。

### 3.3 交互策略优化：建议优先选择父目录
- 如果目录本身文件过多，系统文件选择器在进入这一层时就会卡。
- App 可以在设置说明或提示语中增加建议：
  - 优先选择上级目录
  - 打开“包含子文件夹”
  - 由 App 在后台递归处理

### 3.4 进度反馈优化
- 扫描进度条继续保留，但要保证：
  - 一旦开始后台扫描，文件夹项在列表中可见
  - 当前扫描到多少张、是否完成，都能持续显示
- 可以在文件夹列表中增加一个“扫描中”状态文字，避免用户误以为失败。

## 4. 验证计划
1. 选择一个包含 10000+ 图片的目录，确认点击“使用此文件夹”后文件夹能立即出现在列表中。
2. 扫描过程中 UI 不冻结，进度条持续更新。
3. 扫描完成后总图片数正确增长。
4. 对比优化前后，确认大目录导入速度明显提升。
5. 验证选择父目录 + 包含子文件夹场景也能正常完成。
